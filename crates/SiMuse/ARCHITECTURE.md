# SiMuse backend

SiMuse — вычислительная часть проекта. Он не является игровым миром и не
управляет существами напрямую. Его задача — быстро и воспроизводимо считать
нейроны, пластичность, рост коннектомов и формат состояния.

## Роль в игре

```text
Dioma game
  └─ dioma-engine
       ├─ Creature / Blood / Arena
       └─ SiMuse
            ├─ pillars          CPU SIMD
            ├─ pillars-wgpu     GPU wgpu
            ├─ prometheus-grow  рост коннектома
            └─ taas-format      save/replay
```

`dioma-engine` владеет игровой семантикой. SiMuse владеет вычислительными
примитивами. Это разделение не позволяет оптимизациям backend случайно менять
правила мира.

## Компоненты

### `pillars`

CPU-ядро нейронных популяций. Подходит для:

- маленьких мозгов;
- headless режима и тестов;
- CPU fallback при отсутствии GPU;
- эталонных сравнений.

### `pillars-wgpu`

GPU-путь для LIF/alpha-LIF и массового исполнения. Он особенно эффективен,
когда несколько мозгов объединены в batch. Для одиночного маленького мозга
CPU может быть быстрее из-за dispatch/readback overhead.

### `prometheus-grow`

Рост проводки и диффузия морфогенов. На выходе получается `Grown`:
топология, регионы, типы связей и стартовые веса.

### `taas-format`

Игровой бинарный формат секций TAAS2 для сохранений и replay. Формат должен
оставаться независимым от конкретной реализации CPU/GPU.

## Контракт CPU/GPU

CPU и GPU обязаны совпадать по игровой семантике:

- одинаковые входные токи;
- одинаковые spike/action decisions;
- одинаковое применение награды;
- одинаковые ограничения весов;
- одинаковая детерминированность, если backend заявляет bit-exact режим.

Допустимые различия f32/f64 должны быть явно отражены в тестовом допуске.
Нельзя скрывать рассинхронизацию за «похожим поведением».

## Горячие правила производительности

1. Не загружать веса на GPU каждый подшаг, если они не менялись.
2. Не делать синхронный `map_async` после каждого подшага.
3. Накопленные спайки читать пачкой, если пластичность не требует немедленного
   результата.
4. Сначала измерять dispatch, upload, readback и kernel отдельно.
5. Сравнивать CPU и GPU на одинаковом числе существ и одинаковом числе тиков.
6. Для маленьких мозгов использовать CPU без чувства вины — это ожидаемый
   latency crossover, а не ошибка архитектуры.

## Жизненный цикл данных

```text
Genome / Layout
      ↓
Prometheus grow
      ↓
Grown (рождение)
      ↓
Brain backend (CPU или GPU)
      ↓
spikes / actions
      ↓
Dioma engine
      ↓
reward, sleep, offspring, save
```

`Grown` нельзя путать с текущими обученными весами. При рождении ребёнка
наследуется генетическая база проводки, а выученный опыт передаётся только
через явно сформированные инстинкт-гены.

## Изменение API

Перед изменением публичного API нужно ответить:

- нужен ли метод игровому движку или только benchmark;
- должен ли он работать на CPU fallback;
- нужна ли ему синхронизация с GPU;
- можно ли выполнить операцию batch-ом;
- как она влияет на replay и сохранение;
- какой headless-тест доказывает правильность.

Новые GPU-методы должны иметь CPU-аналог или документированный reason,
почему аналог невозможен.

## Проверка изменений

Из корня Dioma:

```bash
cargo check -p dioma-engine
cargo test -p dioma-engine --lib
cargo build --workspace --all-targets
cargo test --workspace
```

Для изменений `pillars` дополнительно:

```bash
cargo test --manifest-path crates/SiMuse/crates/pillars/Cargo.toml --lib
```

Поведенческий тест важнее одного успешного build: он должен прогонять полный
путь «вход → вычисление → spike/action → изменение состояния».
